# 列车创作者接入教程

[English](CREATOR_GUIDE.en.md) · [日本語](CREATOR_GUIDE.ja.md) · [简体中文](CREATOR_GUIDE.zh-CN.md)

适用：Train ReDoor 1.2.0 / 运行时 1.2.0.0。本文描述现有实现，不代表已经完成游戏内验收。

## 1. 工作原理与前提

控制器注册在渲染阶段、游戏动画准备之前。只处理同时具有 `Train`、`PrefabRef`、`InterpolatedTransform`、`Bone` 和 `Skeleton` 的运行实体。它读取 `BoardingLeft` / `BoardingRight`，用模拟时间计算左右开度，再从绑定位置加上平移。暂停时模拟时间不推进，门保持开度。

每个被控制的渲染网格需要有效 `ProceduralAnimationProperties`、`ProceduralBone`、骨骼绑定索引和蒙皮。只有用途 `None=0` 的门骨参与。转向架、受电弓、贯通道等继续使用自己的用途。

这意味着“有个叫 Door 的物体”不够：没有骨架/蒙皮的整块车壳不会自动切出门，也不会因为修改网格名就开门。不能保证所有地铁、其他交通种类都满足实体条件；请先核对实际运行实体，别仅凭车辆名称判断。

## 2. 在 Blender 准备门与蒙皮

1. 保存原工程的独立版本。保持建模单位、实车尺寸与作者既定的轨距设计一致。控制器不修改模型尺寸或轨距。
2. 在“完全关门”状态设置绑定姿态。移动门板、随门玻璃、胶条、压条都属于门；固定门框与门袋属于车身。
3. 每扇独立运动的门使用相应骨骼与顶点组。刚性门板通常将对应顶点完整赋权给门骨；避免混入车身权重导致拉伸。
4. 保持骨架与车体变换一致。在绑定前按自身流程确定缩放与轴向；不要绑定后盲目应用变换、清空父级或修改绑定姿态。
5. 父骨坐标与游戏原生车辆轴向一致时，可使用标准命名。若父骨被旋转，标准 +Z/-Z 可能不是车身纵向，需修正骨架或使用父坐标 JSON 位移。
6. 车体和独立玻璃分别导出时，两套蒙皮都必须保留相应门骨和一致的绑定位置；只给车壳加骨无法驱动另一份静态玻璃。
7. 可将多个位置、同侧且同方向运动的门绑定到共享骨，前提是它们需要完全相同行程。每组独立骨通常更易排错。

插件无需预制开门动画剪辑。建模软件里拖动骨骼只验证蒙皮；游戏运营才验证站台信号和轴向。

## 3. 推荐的自动命名

格式：`ReDoor_<L或R>_<正整数门组>_<0或1>_<毫米行程>`。也接受 `TrainReDoor_` 前缀。匹配区分大小写。

一组门、另一组门、另一侧可以分别命名：

```text
ReDoor_L_01_0_850
ReDoor_L_01_1_850
ReDoor_L_02_0_850
ReDoor_L_02_1_850
ReDoor_R_01_0_850
ReDoor_R_01_1_850
```

| 字段 | 规则 |
| --- | --- |
| `ReDoor` | 显式选择本控制器，不能省略 |
| `L/R` | 作者侧别标记，实际站台侧按原生骨位置 X 判断 |
| `01` | 正整数，允许前导零；没有原先 1～4 的限制，最大为 Int32 正整数 |
| `0` | 相对于绑定姿态沿父坐标 +Z 平移 |
| `1` | 沿父坐标 -Z 平移，不是另一种站台侧 |
| `850` | 行程 850 mm；合法范围 1～10000 mm，可用小数点，例如 `640.5` |

**方向与侧别独立。** 原生 object X<0 对应 Left，X>0 对应 Right。`abs(X)<0.0001` m 无法自动判侧，需 JSON 显式 Left/Right。字面 L/R 可能因导出轴转换与原生坐标相反，不要仅改名字反复“修正”站台侧。

原生父轴中 X 为横向、Y 为竖向、Z 为纵向。教程中的 +Z/-Z 是游戏坐标，不是承诺 Blender 视图中的某个轴。门往门缝中心合拢而非分开时，检查方向位 0/1、父骨旋转及实际导出轴。


## 4. 导入游戏资产编辑器

通过游戏的车辆资产流程导入带骨架/蒙皮的 FBX，保留已有车包需要的材质和渲染配置。检查实际 RenderPrefab 的程序骨骼：门骨用途为 `None=0`，绑定索引有效，绑定姿态为关门位置。其他骨的用途保持正确。

车体与玻璃若是独立 RenderPrefab，要逐份检查它们的程序动画与骨信息；玻璃材质透明设置由车包完成，本插件不替换 Surface。确认导入后的长度、宽度、轮位与轨距，不要把毫米直接当作游戏位移米。

保存并重新加载资产，确认骨信息仍存在。编辑器静态预览没有运营上下客信号，门不动不能单独证明插件失败。需要实际线路运行列车。

## 5. 任意骨名：JSON 精确映射

完整可解析文件见 [CustomTrain.example.json](../examples/CustomTrain.example.json)。条目示例：

```json
{
  "mesh": "MyTrain",
  "bone": "PassengerDoor_A",
  "side": "Auto",
  "deltaMeters": [0, 0, 0.85]
}
```

把条目放入**控制器正在读取的** `TrainReDoor.json` 的 `bindings` 数组。`mesh` 必须是游戏实际 RenderPrefab 名，不能把平台标题、Blender 对象名或猜测的资产名称当作等价项。骨名也精确区分大小写。主体和独立玻璃用各自实际网格名各写一份。

`side` 只接受 `Left`、`Right`、`Auto`。Auto 按原生 X 判侧；显式侧别可以处理中心线骨。`deltaMeters` 是骨父坐标中的三分量**米**位移，长度 0.001～10 m；`[0,0,0.85]` = 850 mm。这可描述一条斜线的平移，但不是“先外推、再滑动”的多阶段塞拉门。


配置只在插件加载时读取，修改后重启游戏。格式错误、重复 mesh/bone、无效侧别或越界参数会使自定义配置整体回退默认值，并写错误日志；不是保留部分正确条目。

**当前没有每车包 JSON 自动发现、合并或插件注册 API。** 在车包目录放 `MyTrain.json` 不会自动生效；下载更新可能覆盖控制器旁的手改配置。公开车包优先选择自动命名，避免要求玩家改共享配置。

## 6. 安装、运营检查与排错


日志应看到 `[Train ReDoor 1.2.0] Loaded`，以及相应网格的 `Bound ... moving door bones`。日志里的配置路径才是实际读取位置。Bound 只证明找到了骨，不能证明蒙皮或方向正确。

| 现象 | 优先检查 |
| --- | --- |
| 没有 Loaded | 播放集、DLL 是否加载、其他控制器干扰、游戏兼容性 |
| Loaded 但没有对应 Bound | Train 实体条件、RenderPrefab、骨名、None 用途、绑定索引、排除配置 |
| 门板动、玻璃不动 | 独立玻璃的蒙皮、对应门骨和程序动画数据 |
| 错侧开门 | 原生 object X、导出轴、显式 JSON side，不能只看 L/R 字面 |
| 门移动方向错误 | 方向位 0/1、父坐标旋转、JSON 向量 |
| 门扇变形或车身被拉动 | 顶点权重、绑定姿态、车身顶点是否误绑门骨 |
| 改 JSON 无效 | Loaded 日志的配置路径、重启、解析错误、精确网格名 |
| 编辑器门不动 | 是否只有静态预览，没有线路 Boarding 信号 |

测试左右站台、反向编组、暂停恢复、上下客结束、双侧信号（有可复现条件时）、保存重载，以及无关骨骼保持正常。记录游戏版本、模型版本、运行时版本和结果；未执行的项目记为未执行。详见 [VALIDATION](VALIDATION.zh-CN.md)。

当前控制器不等待门完全关闭才允许发车。不要宣传发车联锁、声效、乘客路径或碰撞。

## 7. 发布自己的车包

将已有 Train ReDoor 条目（Mod ID 164831）加到车包依赖，不要填写示例 ID 或重传自己的控制器副本。发布资产本体并注明所需控制器版本；通常不需要上传插件源码，也不必编译 C#。


自动识别仅使用 ReDoor/TrainReDoor 公共规范，任意其他骨名应改名或使用精确 JSON 映射。开关时间为全局 0.05～60 模拟秒，优先级为排除网格 > JSON > 通用命名。安装时启用一个控制器，避免多个门控制器同时接管。测试使用独立编写的通用合成案例，不宣称模型或游戏验收。
